Modelagem de usuários, perfis e permissões com Spring Security

Nome do projeto backend: backend-api
Tecnologia Principal: Maven, Java 17, Lombok, Spring Boot 3, Docker com o container do
Banco de dado Mysql 8.
Base de dados: "bd_paytur"
Foco Inicial: Estrutura de autenticação com Spring Security para Autenticação, administração de usuarios, permissoes e grupos de permissoes.

O objetivo é estruturar a autenticação e a autorização do sistema `JulyTurAdm`, utilizando o
Spring Security com usuários persistidos no banco `bd_paytur`, perfis de acesso (Roles) e 
permissões granulares (Authorities).

A análise considera o modelo de negócio descrito: o DBA prepara o acesso inicial, o Administrador
Master estabelece o acesso do setor de Recursos Humanos (RH), e o RH cadastra os colaboradores e 
associa seus acessos aos módulos correspondentes, como Contas a Pagar, Cobrança, Contabilidade e
Reservas.

Minha recomendação principal: manter as cinco tabelas propostas, corrigir algumas inconsistências
no SQL e implementar a autorização em duas camadas: perfis funcionais para agrupar responsabilidades
e permissões granulares para determinar as operações permitidas.

Essa estrutura permite evoluir a aplicação sem precisar criar um mecanismo de segurança diferente 
para cada módulo.

1. Arquitetura conceitual

Usuário (`users`)

Identidade, e-mail, senha criptografada e situação da conta

N:N — `users_roles`

Perfil / Role (`roles`)

Agrupa responsabilidades, por exemplo `ROLE_CONTAS_PAGAR`

N:N — `roles_permissions`

Permissão (`permissions`)

Define operações específicas, por exemplo `contas-pagar:UPDATE`

O fluxo de autorização será:

1. O usuário apresenta suas credenciais.
2. O Spring Security autentica o usuário e senha.
3. A aplicação carrega os perfis e as permissões associados ao usuário.
4. O Spring Security cria as `GrantedAuthority` correspondentes.
5. As regras de segurança verificam se o usuário pode executar a operação solicitada.

Distinção fundamental: autenticação responde quem é o usuário?; autorização responde o que esse
usuário pode fazer?

2. Análise das cinco tabelas

2.1. Tabela `users` — cadastro de usuários


| Campo        | Recomendação                             |
| ------------ | ---------------------------------------- |
| `id`         | Chave primária numérica                  |
| `name`       | Nome completo do colaborador             |
| `email`      | Login único, obrigatório                 |
| `password`   | Hash da senha, nunca senha em texto puro |
| `enabled`    | Indica se a conta está habilitada        |
| `created_at` | Data de criação                          |
| `updated_at` | Data da última alteração                 |

Recomendo que o e-mail seja normalizado antes da persistência, por exemplo removendo espaços nas
extremidades e adotando uma regra consistente de letras minúsculas.

A validação da aplicação e a restrição `UNIQUE` no MySQL devem trabalhar em conjunto.

Para o campo `enabled`, a aplicação deverá impedir a autenticação de contas desabilitadas.
A exclusão ou o desligamento de colaboradores merece uma política própria; em sistemas administrativos,
desabilitar a conta costuma preservar melhor o histórico.

---------------------------------------------------------------------------------------------------
2.2. Tabela `roles` — perfis funcionais

Os seguintes perfis são adequados para agrupar as responsabilidades dos colaboradores:

- `ADMIN`
- `RECURSOS_HUMANOS`
- `CONTAS_PAGAR`
- `COBRANCA`
- `CONTABIL`
- `RESERVAS`


Para verificar diretamente uma permissão granular, a aplicação poderá usar:

@PreAuthorize("hasAuthority('contas-pagar:UPDATE')")

Os perfis devem ser nomes estáveis, sem espaços, e únicos no banco.

A descrição amigável, como “Contas a Pagar”, pode ser apresentada na interface sem alterar o identificador técnico.

---------------------------------------------------------------------------------------------------
2.3. Tabela `permissions` — permissões granulares

Sua ideia de separar as permissões dos perfis é boa.

Ela permite controlar as ações por módulo, sem precisar criar um perfil diferente para cada combinação
de operações.

Sugiro padronizar os nomes em letras maiúsculas, mantendo um formato uniforme:

| Módulo           | Inserir                   | Consultar                 | Atualizar                 | Excluir                   |
| ---------------- | ------------------------- | ------------------------- | ------------------------- | ------------------------- |
| Administração    | `ADMIN:INSERT`            | `ADMIN:SELECT`            | `ADMIN:UPDATE`            | `ADMIN:DELETE`            |
| Recursos Humanos | `RECURSOS_HUMANOS:INSERT` | `RECURSOS_HUMANOS:SELECT` | `RECURSOS_HUMANOS:UPDATE` | `RECURSOS_HUMANOS:DELETE` |
| Contas a Pagar   | `CONTAS_PAGAR:INSERT`     | `CONTAS_PAGAR:SELECT`     | `CONTAS_PAGAR:UPDATE`     | `CONTAS_PAGAR:DELETE`     |
| Cobrança         | `COBRANCA:INSERT`         | `COBRANCA:SELECT`         | `COBRANCA:UPDATE`         | `COBRANCA:DELETE`         |
| Contabilidade    | `CONTABIL:INSERT`         | `CONTABIL:SELECT`         | `CONTABIL:UPDATE`         | `CONTABIL:DELETE`         |
| Reservas         | `RESERVAS:INSERT`         | `RESERVAS:SELECT`         | `RESERVAS:UPDATE`         | `RESERVAS:DELETE`         |

O Spring Security não exige que esses identificadores sejam escritos em maiúsculas.

A padronização é uma decisão de projeto que facilita a manutenção, os testes e a revisão das regras.

Também é importante corrigir um ponto da observação original: espaços em nomes de autoridades não
corrompem automaticamente um token.

Ainda assim, identificadores técnicos sem espaços são mais previsíveis, especialmente quando forem
incluídos em JWTs ou utilizados em expressões de autorização.

---------------------------------------------------------------------------------------------------
2.4. Tabela `users_roles` — associação entre usuários e perfis

A chave primária composta (`user_id`, `role_id`) é apropriada: ela impede que o mesmo perfil seja
associado duas vezes ao mesmo usuário.

Exemplo conceitual:

| Usuário                      | Perfil                  |
| ---------------------------- | ----------------------- |
| Administrador Master         | `ADMIN`                 |
| João Silva Benavides         | `RECURSOS_HUMANOS`      |
| Pedro Orlando Yanez Figueroa | `CONTAS_PAGAR`          |
| Marcos Antonio Figueroa      | `COBRANCA`              |

Essas associações são ilustrativas; o acesso real deve depender dos perfis e das permissões 
efetivamente atribuídos.

Revisão das regras `ON DELETE`.

Atualmente, a exclusão de um usuário é restringida enquanto existirem associações, mas a exclusão
de um perfil pode apagar as associações desse perfil em `users_roles`.

Para um sistema empresarial, eu priorizaria a desativação de usuários e perfis em vez da exclusão física,
preservando a rastreabilidade.

---------------------------------------------------------------------------------------------------
2.5. Tabela `roles_permissions` — associação entre perfis e permissões

A chave composta (`role_id`, `permission_id`) também está correta.

A principal regra de negócio será: um perfil concede somente as permissões explicitamente associadas
a ele.

Por exemplo, um perfil `CONTAS_PAGAR` poderá receber:

- `CONTAS_PAGAR:INSERT`
- `CONTAS_PAGAR:SELECT`
- `CONTAS_PAGAR:UPDATE`

Se não receber `CONTAS_PAGAR:DELETE`, seus usuários não deverão conseguir excluir registros.

O mesmo perfil pode ser atribuído a vários colaboradores, e uma permissão pode pertencer a vários perfis.

Essa flexibilidade é justamente a vantagem do modelo relacional N:N.

4. Modelo SQL revisado para o MySQL 8

Abaixo está uma versão inicial corrigida das cinco tabelas.

Mantive o modelo relacional original, ajustando o campo de login, a padronização dos nomes e os índices
das tabelas associativas.

> Execute este script somente depois de confirmar o estado atual do banco `bd_paytur`.
Se as tabelas já existirem, será necessário criar uma migração em vez de executar novamente os comandos `CREATE TABLE`.

```
USE bd_paytur;

CREATE TABLE users (
    id BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL,
    password VARCHAR(255) NOT NULL,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    PRIMARY KEY (id),
    CONSTRAINT UK_users_email UNIQUE (email)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci;


CREATE TABLE roles (
    id BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,

    PRIMARY KEY (id),
    CONSTRAINT UK_roles_name UNIQUE (name)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci;


CREATE TABLE permissions (
    id BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(80) NOT NULL,

    PRIMARY KEY (id),
    CONSTRAINT UK_permissions_name UNIQUE (name)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci;


CREATE TABLE users_roles (
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,

    PRIMARY KEY (user_id, role_id),
    INDEX IX_users_roles_role_id (role_id),

    CONSTRAINT FK_ur_user
        FOREIGN KEY (user_id)
        REFERENCES users (id)
        ON DELETE RESTRICT,

    CONSTRAINT FK_ur_role
        FOREIGN KEY (role_id)
        REFERENCES roles (id)
        ON DELETE RESTRICT
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci;


CREATE TABLE roles_permissions (
    role_id BIGINT NOT NULL,
    permission_id BIGINT NOT NULL,

    PRIMARY KEY (role_id, permission_id),
    INDEX IX_roles_permissions_permission_id (permission_id),

    CONSTRAINT FK_rp_role
        FOREIGN KEY (role_id)
        REFERENCES roles (id)
        ON DELETE RESTRICT,

    CONSTRAINT FK_rp_permission
        FOREIGN KEY (permission_id)
        REFERENCES permissions (id)
        ON DELETE RESTRICT
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci;
```

Por que essas alterações?

- `email`: elimina a inconsistência entre `user_name` e `email`.
- `BOOLEAN`: expressa claramente o estado habilitado/desabilitado; no MySQL, é um alias de `TINYINT(1)`.
- Índices nas chaves estrangeiras inversas: facilitam consultas que partem de um perfil ou de uma permissão.
- `ON DELETE RESTRICT`: impede a exclusão física de perfis e permissões enquanto houver associações.
   É uma política conservadora; os desligamentos devem preferencialmente ser tratados por desativação.
- `utf8mb4`: permite armazenar nomes com caracteres acentuados.

A chave primária composta nas tabelas de relacionamento continua impedindo associações duplicadas.
