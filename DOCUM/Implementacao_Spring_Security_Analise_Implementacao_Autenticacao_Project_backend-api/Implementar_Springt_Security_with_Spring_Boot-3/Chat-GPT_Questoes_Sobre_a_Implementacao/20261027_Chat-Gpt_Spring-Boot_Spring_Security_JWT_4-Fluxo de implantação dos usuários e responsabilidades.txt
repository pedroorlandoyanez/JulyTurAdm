Fluxo de implantação dos usuários e responsabilidades

O processo de cadastro precisa de uma regra de segurança especial: o primeiro administrador não pode
depender de um endpoint público de cadastro que permita a qualquer pessoa criar uma conta com poderes
administrativos.

Etapa 1 — Preparação pelo DBA

O DBA prepara os dados iniciais:

1. Cria o perfil `ADMIN`.
2. Cria as quatro permissões administrativas.
3. Associa essas permissões ao perfil `ADMIN`.
4. Cria o usuário inicial Administrador Master, com senha armazenada como hash.
5. Associa o usuário ao perfil administrativo.

O banco não deve receber a senha em texto puro.

O hash deve ser gerado pelo `PasswordEncoder` da aplicação ou por um procedimento controlado que
utilize o mesmo algoritmo de codificação.

O usuário Master deve ser criado por um processo de inicialização restrito, executado apenas quando
necessário, ou por uma ferramenta administrativa segura.

Não recomendo disponibilizar uma rota pública como `/api/users/master`.

Etapa 2 — Administração de Recursos Humanos

O Administrador Master concede ao responsável de RH o perfil `RECURSOS_HUMANOS`, que deverá receber
somente as permissões necessárias para a gestão dos colaboradores.

A partir daí, o RH poderá cadastrar usuários comuns e associar os perfis autorizados pela política
da empresa.

Importante: o RH não deve receber automaticamente `ADMIN`.

A capacidade de cadastrar usuários não deve significar capacidade irrestrita de conceder privilégios
administrativos.

Etapa 3 — Contratação para Contas a Pagar

Novo colaborador contratado

O RH registra nome, e-mail e os dados necessários do colaborador.

Atribuição de perfil:

O RH atribui `CONTAS_PAGAR`, desde que essa operação esteja autorizada pela política de acesso.

Permissões efetivas

O sistema carrega somente as autoridades associadas ao perfil, por exemplo consulta e atualização.

Acesso controlado

O colaborador acessa apenas as funcionalidades permitidas, inclusive respeitando as regras de negócio
e o escopo dos dados.

Um ponto adicional: permissões como `CONTAS_PAGAR:SELECT` controlam a operação, mas não garantem,
sozinhas, que o usuário veja apenas os registros que lhe competem.

Caso haja segregação por filial, empresa ou departamento, será necessário implementar também 
controles de escopo dos dados.

Matriz de permissões sugerida:

A tabela a seguir representa uma proposta inicial de autorização. As associações efetivas deverão ser
definidas e gravadas em `roles_permissions`.

| Perfil             | Inserir              | Consultar            | Atualizar            | Excluir             |
| ------------------ | -------------------- | -------------------- | -------------------- | ------------------- |
| `ADMIN`            | Administração        | Administração        | Administração        | Administração       |
| `RECURSOS_HUMANOS` | Usuários autorizados | Usuários autorizados | Usuários autorizados | Conforme política   |
| `CONTAS_PAGAR`     | Conforme atribuição  | Conforme atribuição  | Conforme atribuição  | Conforme atribuição |
| `COBRANCA`         | Conforme atribuição  | Conforme atribuição  | Conforme atribuição  | Conforme atribuição |
| `CONTABIL`         | Conforme atribuição  | Conforme atribuição  | Conforme atribuição  | Conforme atribuição |
| `RESERVAS`         | Conforme atribuição  | Conforme atribuição  | Conforme atribuição  | Conforme atribuição |

Não recomendo conceder exclusão a todos os perfis por padrão.

Em módulos financeiros, operações destrutivas podem exigir restrições adicionais, auditoria ou fluxos
de aprovação.

Também vale definir se o Administrador Master será um usuário operacional comum com um perfil especial
ou uma identidade de emergência administrativa.

Em ambientes empresariais, separar as duas finalidades pode reduzir riscos.
