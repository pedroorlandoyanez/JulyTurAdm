Como o Spring Security interpreta as convenções do banco.

O Spring Security não interpreta automaticamente os registros das tabelas `users`, `roles` e `permissions`.

É a aplicação Java que deve carregar esses registros e convertê-los em `GrantedAuthority`.

A distinção é importante:

- Perfil funcional — User.

`ADMIN`
`Joao Benavides`
`Pedro Orlando`

- Perfil funcional — Role.

Tabela `roles`

`ADMIN`
`CONTAS_PAGAR`
`RECURSOS_HUMANOS`
`CONTABILIDADE`

Identifica o grupo de responsabilidades atribuído ao colaborador.

- Permissões granulares — Permissions.

Tabela `permissions`

`CONTAS_PAGAR:INSERT`
`CONTAS_PAGAR:UPDATE`
`CONTAS_PAGAR:SELECT`
`CONTAS_PAGAR:DELETE`

Determinam quais operações específicas podem ser executadas.

Autoridades efetivas — GrantedAuthority.

Objetos carregados na autenticação

`CONTAS_PAGAR`

`CONTAS_PAGAR:INSERT`
`CONTAS_PAGAR:UPDATE`
`CONTAS_PAGAR:SELECT`
`CONTAS_PAGAR:DELETE`

...

São as autoridades que o Spring Security consulta durante a autorização.

Uma correção importante sobre a nomenclatura

Você definiu que o banco armazenará o perfil como `CONTAS_PAGAR`.

Essa convenção pode e deve ser mantida.

Entretanto, o Spring Security possui duas formas de verificar autoridades:

- `hasRole("CONTAS_PAGAR")`: por convenção, procura a autoridade `ROLE_CONTAS_PAGAR`.
- `hasAuthority("CONTAS_PAGAR:UPDATE")`: procura exatamente a autoridade `CONTAS_PAGAR:UPDATE`.

Portanto, recomendo preservar os nomes originais no banco e adicionar o prefixo `ROLE_` somente ao
converter os perfis em autoridades Java.

*Não adicione esse prefixo ao nome armazenado na tabela `roles`.

2. Exemplo prático: colaborador de Contas a Pagar

Imagine que o banco contenha estas associações:


Tabela `users`

| `id` | `name`               | `email`                    | `password`  | `enabled`
| ---- | -------------------- | -------------------------- | ----------- | ---------
| 1    | `ADMIN`              | `adm@julytur.com           | #########   | TRUE
| 15   | `Joao Benavides`     | `joaoBenavides@julytur.com | #########   | TRUE
| 16   | `Pedro Orlando`      | `pedroOrlando@julytur.com  | #########   | TRUE

---

Tabela `users_roles`

| `user_id` | `role_id` | Perfil             |
| --------- | --------- | ------------------ |
| 15        | 3         | `CONTAS_PAGAR`     |
| 16        | 4         | `RECURSOS_HUMANOS` |


Tabela `roles_permissions`

| `role_id` | `permission_id` | Permissão             |
| --------- | --------------- | --------------------- |
| 3         | 8               | `CONTAS_PAGAR:INSERT` |
| 3         | 9               | `CONTAS_PAGAR:UPDATE` |
| 3         | 10              | `CONTAS_PAGAR:SELECT` |
| 3         | 11              | `CONTAS_PAGAR:DELETE` |

Nesse cenário, o colaborador não tem permissão para inserir ou excluir registros.

Após a autenticação, as autoridades efetivas serão:

```
CONTAS_PAGAR
CONTAS_PAGAR:INSERT
CONTAS_PAGAR:UPDATE
CONTAS_PAGAR:SELECT
CONTAS_PAGAR:DELETE

```
O resultado esperado é:

| Operação                          | Resultado |
| --------------------------------- | --------- |
| Verificar o perfil `CONTAS_PAGAR` | Permitido |
| Consultar contas a pagar          | Permitido |
| Atualizar uma conta a pagar       | Permitido |
| Inserir uma conta a pagar         | Permitido |
| Excluir uma conta a pagar         | Negado    |

Isso depende de as associações estarem corretamente gravadas em `roles_permissions` e de a 
aplicação carregar todas as autoridades associadas ao usuário.

Segue estrutura de tabelas do banco de dados 'bd_paytur'

```
CREATE TABLE users (
    id BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL,
    password VARCHAR(255) NOT NULL,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    PRIMARY KEY (id),
    CONSTRAINT UK_users_email UNIQUE (email)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci;


CREATE TABLE roles (
    id BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,

    PRIMARY KEY (id),
    CONSTRAINT UK_roles_name UNIQUE (name)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci;


CREATE TABLE permissions (
    id BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(80) NOT NULL,

    PRIMARY KEY (id),
    CONSTRAINT UK_permissions_name UNIQUE (name)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci;


CREATE TABLE users_roles (
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,

    PRIMARY KEY (user_id, role_id),
    INDEX IX_users_roles_role_id (role_id),

    CONSTRAINT FK_ur_user
        FOREIGN KEY (user_id)
        REFERENCES users (id)
        ON DELETE RESTRICT,

    CONSTRAINT FK_ur_role
        FOREIGN KEY (role_id)
        REFERENCES roles (id)
        ON DELETE RESTRICT
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci;


CREATE TABLE roles_permissions (
    role_id BIGINT NOT NULL,
    permission_id BIGINT NOT NULL,

    PRIMARY KEY (role_id, permission_id),
    INDEX IX_roles_permissions_permission_id (permission_id),

    CONSTRAINT FK_rp_role
        FOREIGN KEY (role_id)
        REFERENCES roles (id)
        ON DELETE RESTRICT,

    CONSTRAINT FK_rp_permission
        FOREIGN KEY (permission_id)
        REFERENCES permissions (id)
        ON DELETE RESTRICT
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci;
```

Por que essas alterações?

- `email`: elimina a inconsistência entre `user_name` e `email`.
- `BOOLEAN`: expressa claramente o estado habilitado/desabilitado; no MySQL, é um alias de `TINYINT(1)`.
- Índices nas chaves estrangeiras inversas: facilitam consultas que partem de um perfil ou de uma permissão.
- `ON DELETE RESTRICT`: impede a exclusão física de perfis e permissões enquanto houver associações.
   É uma política conservadora; os desligamentos devem preferencialmente ser tratados por desativação.
- `utf8mb4`: permite armazenar nomes com caracteres acentuados.

A chave primária composta nas tabelas de relacionamento continua impedindo associações duplicadas.
