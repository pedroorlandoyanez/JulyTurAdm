Análise técnica: Spring Security, Roles e Authorities no projeto `backend-api`

A sua modelagem para o sistema `JulyTurAdm` está bem direcionada.

A principal decisão arquitetural é manter os perfis funcionais (`roles`) separados das permissões
granulares (`permissions`), utilizando o Spring Security para transformar os dados persistidos no
MySQL 8 em autoridades reconhecidas pela aplicação.

Considerando o ambiente — Java 17, Maven, Spring Boot 3, Lombok, Hibernate/JPA e MySQL 8 — 
recomendo implementar essa estrutura com as versões de Spring Security gerenciadas pelo Spring Boot 3.

---------------------------------------------------------------------------------------------------
1. Como o Spring Security interpreta as convenções do banco

O Spring Security não interpreta automaticamente os registros das tabelas `roles` e `permissions`.

É a aplicação Java que deve carregar esses registros e convertê-los em `GrantedAuthority`.

A distinção é importante:

1. Perfil funcional — Role

Tabela `roles`

`CONTAS_PAGAR`

Identifica o grupo de responsabilidades atribuído ao colaborador.

2. Permissões granulares — Permissions

Tabela `permissions`

`CONTAS_PAGAR:SELECT`

`CONTAS_PAGAR:UPDATE`

Determinam quais operações específicas podem ser executadas.

---------------------------------------------------------------------------------------------------
3. Autoridades efetivas — GrantedAuthority

Objetos carregados na autenticação

`CONTAS_PAGAR`

`CONTAS_PAGAR:SELECT`
`CONTAS_PAGAR:UPDATE`
...

São as autoridades que o Spring Security consulta durante a autorização.

Uma correção importante sobre a nomenclatura

Você definiu que o banco armazenará o perfil como `CONTAS_PAGAR`.

Essa convenção pode e deve ser mantida.

Entretanto, o Spring Security possui duas formas de verificar autoridades:

- `hasRole("CONTAS_PAGAR")`: por convenção, procura a autoridade `ROLE_CONTAS_PAGAR`.
- `hasAuthority("CONTAS_PAGAR:UPDATE")`: procura exatamente a autoridade `CONTAS_PAGAR:UPDATE`.

Portanto, recomendo preservar os nomes originais no banco e adicionar o prefixo `ROLE_` somente ao
converter os perfis em autoridades Java.

*Não adicione esse prefixo ao nome armazenado na tabela `roles`.

---------------------------------------------------------------------------------------------------
2. Exemplo prático: colaborador de Contas a Pagar

Imagine que o banco contenha estas associações:

Tabela `users_roles`

| `user_id` | `role_id` | Perfil         |
| --------- | --------- | -------------- |
| 15        | 3         | `CONTAS_PAGAR` |

Tabela `roles_permissions`

| `role_id` | `permission_id` | Permissão             |
| --------- | --------------- | --------------------- |
| 3         | 8               | `CONTAS_PAGAR:SELECT` |
| 3         | 9               | `CONTAS_PAGAR:UPDATE` |

Nesse cenário, o colaborador não tem permissão para inserir ou excluir registros.

Após a autenticação, as autoridades efetivas serão:

```
CONTAS_PAGAR
CONTAS_PAGAR:SELECT
CONTAS_PAGAR:UPDATE
```

O resultado esperado é:

| Operação                          | Resultado |
| --------------------------------- | --------- |
| Verificar o perfil `CONTAS_PAGAR` | Permitido |
| Consultar contas a pagar          | Permitido |
| Atualizar uma conta a pagar       | Permitido |
| Inserir uma conta a pagar         | Negado    |
| Excluir uma conta a pagar         | Negado    |

Isso depende de as associações estarem corretamente gravadas em `roles_permissions` e de a 
aplicação carregar todas as autoridades associadas ao usuário.

3.1. Entidade `Permission`

A entidade representa cada registro da tabela `permissions`.

```

package br.com.julyturadm.permission;

import jakarta.persistence.*;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;

@Entity
@Table(name = "permissions")
@Getter
@Setter
@NoArgsConstructor
public class Permission {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 80)
    private String name;
}

```

Atenção: para eliminar qualquer ambiguidade no exemplo anterior, vou usar daqui em diante o pacote Java válido `com.julyturadm`.

O código de `Permission` deve começar assim:

```
package com.julyturadm.permission;
```

O restante da entidade permanece igual, com `@Entity`, `@Table(name = "permissions")` e o campo `name`.

3.2. Entidade `Role`

O perfil possui várias permissões, e uma permissão pode pertencer a vários perfis. O relacionamento JPA representa essa associação N:N.

```

package com.julyturadm.role;

import com.julyturadm.permission.Permission;
import jakarta.persistence.*;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;

import java.util.HashSet;
import java.util.Set;

@Entity
@Table(name = "roles")
@Getter
@Setter
@NoArgsConstructor
public class Role {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 50)
    private String name;

    @ManyToMany(fetch = FetchType.LAZY)
    @JoinTable(
        name = "roles_permissions",
        joinColumns = @JoinColumn(name = "role_id"),
        inverseJoinColumns = @JoinColumn(name = "permission_id")
    )
    private Set<Permission> permissions = new HashSet<>();
}

```

3.3. Entidade `User`

A entidade `User` relaciona os colaboradores aos seus perfis.

```

package com.julyturadm.user;

import com.julyturadm.role.Role;
import jakarta.persistence.*;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;

import java.util.HashSet;
import java.util.Set;

@Entity
@Table(name = "users")
@Getter
@Setter
@NoArgsConstructor
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 100)
    private String name;

    @Column(nullable = false, unique = true, length = 255)
    private String email;

    @Column(nullable = false, length = 255)
    private String password;

    @Column(nullable = false)
    private boolean enabled = true;

    @ManyToMany(fetch = FetchType.LAZY)
    @JoinTable(
        name = "users_roles",
        joinColumns = @JoinColumn(name = "user_id"),
        inverseJoinColumns = @JoinColumn(name = "role_id")
    )
    private Set<Role> roles = new HashSet<>();
}

```

Observação sobre segurança: não retorne a entidade `User` diretamente em respostas REST.

Ela contém o hash da senha e relacionamentos internos.

Para a API, utilize DTOs específicos.

3.4. Repositório com carregamento dos perfis e permissões

Esse é um dos pontos mais importantes da implementação.

O Spring Security precisa carregar todos os perfis do usuário e todas as permissões vinculadas a
esses perfis.

Para evitar consultas incompletas e problemas de carregamento tardio do Hibernate, podemos usar uma
consulta explícita.

```

package com.julyturadm.user;

import org.springframework.data.jpa.repository.*;
import org.springframework.data.repository.query.Param;

import java.util.Optional;

public interface UserRepository
        extends JpaRepository<User, Long> {

    @Query("""
        SELECT DISTINCT u
        FROM User u
        LEFT JOIN FETCH u.roles r
        LEFT JOIN FETCH r.permissions
        WHERE LOWER(u.email) = LOWER(:email)
        """)
    Optional<User> findByEmailWithAuthorities(
        @Param("email") String email
    );
}

```

Essa consulta pressupõe que o campo Java se chama `email` e que os relacionamentos das entidades
correspondem ao modelo SQL definido anteriormente.

O `DISTINCT` ajuda a evitar resultados duplicados quando um usuário possui vários perfis ou
permissões.

3.5. `CustomUserDetailsService`: converter o banco em autoridades

Esta classe é responsável por localizar o usuário no banco e construir o objeto que o Spring Security utilizará durante a autenticação.

Aqui está a implementação central:

```

package com.julyturadm.security;

import com.julyturadm.user.User;
import com.julyturadm.user.UserRepository;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.core.userdetails.*;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.HashSet;
import java.util.Set;

@Service
public class CustomUserDetailsService
        implements UserDetailsService {

    private final UserRepository userRepository;

    public CustomUserDetailsService(
            UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Override
    @Transactional(readOnly = true)
    public UserDetails loadUserByUsername(String email)
            throws UsernameNotFoundException {

        User user = userRepository
            .findByEmailWithAuthorities(email.trim())
            .orElseThrow(() ->
                new UsernameNotFoundException(
                    "Usuário não encontrado"
                )
            );

        Set<SimpleGrantedAuthority> authorities =
            new HashSet<>();

        user.getRoles().forEach(role -> {
            // Perfil: CONTAS_PAGAR
            // Autoridade: ROLE_CONTAS_PAGAR
            authorities.add(
                new SimpleGrantedAuthority(
                    "ROLE_" + role.getName()
                )
            );

            // Permissões: somente as cadastradas no banco
            role.getPermissions().forEach(permission ->
                authorities.add(
                    new SimpleGrantedAuthority(
                        permission.getName()
                    )
                )
            );
        });

        return org.springframework.security.core.userdetails
            .User.withUsername(user.getEmail())
            .password(user.getPassword())
            .disabled(!user.isEnabled())
            .authorities(authorities)
            .build();
    }
}

```

O uso de `@Transactional(readOnly = true)` permite que os relacionamentos `LAZY` sejam acessados 
enquanto a transação está aberta.

Observe também que o código percorre todos os perfis do usuário.

Não utiliza apenas o primeiro perfil encontrado.

O método `.disabled(!user.isEnabled())` impede que contas desabilitadas autentiquem com sucesso.
O hash armazenado no campo `password` será validado pelo mecanismo de autenticação configurado.

3.6. Configuração do Spring Security

É necessário habilitar a autorização por métodos para que as anotações `@PreAuthorize` funcionem.

```

package com.julyturadm.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    public SecurityFilterChain securityFilterChain(
            HttpSecurity http) throws Exception {

        http
            .authorizeHttpRequests(authorize -> authorize
                .anyRequest().authenticated()
            )
            .formLogin(form -> {});

        return http.build();
    }
}

```

Essa configuração utiliza o formulário padrão do Spring Security como exemplo inicial de autenticação.

Para a API REST do `JulyTurAdm`, o mecanismo de login — por exemplo, sessão ou JWT — deverá ser 
definido antes de finalizar a configuração de produção.

Não se deve desabilitar o CSRF indiscriminadamente; a configuração depende do mecanismo de 
autenticação escolhido.

O `BCryptPasswordEncoder` é o responsável por verificar senhas armazenadas como hash.

Ele também deve ser utilizado no processo controlado de criação ou alteração de senhas.

4. Como proteger os endpoints

Com as autoridades carregadas, os controllers podem aplicar regras claras e independentes.

```

package com.julyturadm.contasapagar;

import org.springframework.http.ResponseEntity;
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/contas-pagar")
public class ContasPagarController {

    @GetMapping
    @PreAuthorize(
        "hasAuthority('CONTAS_PAGAR:SELECT')"
    )
    public ResponseEntity<String> consultar() {
        return ResponseEntity.ok("Consulta autorizada");
    }

    @PutMapping("/{id}")
    @PreAuthorize(
        "hasAuthority('CONTAS_PAGAR:UPDATE')"
    )
    public ResponseEntity<Void> atualizar(
            @PathVariable Long id) {

        // A atualização real será executada no Service.
        return ResponseEntity.noContent().build();
    }

    @PostMapping
    @PreAuthorize(
        "hasAuthority('CONTAS_PAGAR:INSERT')"
    )
    public ResponseEntity<String> inserir() {
        return ResponseEntity.ok("Inserção autorizada");
    }

    @DeleteMapping("/{id}")
    @PreAuthorize(
        "hasAuthority('CONTAS_PAGAR:DELETE')"
    )
    public ResponseEntity<Void> excluir(
            @PathVariable Long id) {

        // A exclusão real será executada no Service.
        return ResponseEntity.noContent().build();
    }
}

```

Os métodos de exemplo não implementam operações reais de persistência.

Em produção, devem receber DTOs, validar os dados e executar a lógica de negócio na camada de
serviço.

Quando usar `hasRole` e quando usar `hasAuthority`?

| Expressão                             | Autoridade verificada |
| ------------------------------------- | --------------------- |
| `hasRole('CONTAS_PAGAR')`             | `ROLE_CONTAS_PAGAR`   |
| `hasAuthority('CONTAS_PAGAR')`        | `CONTAS_PAGAR`   |
| `hasAuthority('CONTAS_PAGAR:SELECT')` | `CONTAS_PAGAR:SELECT` |
| `hasAuthority('CONTAS_PAGAR:UPDATE')` | `CONTAS_PAGAR:UPDATE` |

Minha recomendação é utilizar `hasAuthority` para as permissões granulares e reservar `hasRole`
para situações em que uma regra realmente dependa do perfil funcional.

Não é necessário verificar o perfil em todos os endpoints.

Se o objetivo é autorizar uma operação, a permissão granular costuma expressar a regra com maior
precisão.

| Cenário                                         | Resultado esperado                                                             |
| ----------------------------------------------- | ------------------------------------------------------------------------------ |

| Usuário autenticado sem a autoridade necessária | HTTP 403                                                                       |

Esses testes devem incluir tanto o `CustomUserDetailsService` quanto os endpoints protegidos,
preferencialmente com testes de integração usando o MySQL ou um ambiente de testes compatível
com o banco real.

6. Criação segura do Administrador Master

O primeiro administrador merece um procedimento separado do cadastro normal de colaboradores.

Sugiro este fluxo:

1. O DBA prepara os registros de perfis e permissões.
2. Um procedimento administrativo restrito cria o usuário inicial.
3. A senha é codificada pelo `PasswordEncoder` configurado na aplicação.
4. O usuário recebe o perfil administrativo e as permissões explicitamente definidas.
5. O acesso inicial é validado e a senha provisória, se utilizada, é trocada.

O hash deve ser produzido assim:

```
String passwordHash =
    passwordEncoder.encode(senhaProvisoria);
```

A variável `senhaProvisoria` deve vir de um mecanismo seguro de provisionamento, nunca de uma senha
fixa gravada no código-fonte.

O hash retornado é o valor que será persistido em `users.password`.

Além disso, o cadastro de colaboradores pelo RH deve validar quais perfis esse operador pode atribuir.

Não basta proteger o endpoint de cadastro: também é necessário impedir que um usuário de RH atribua `ADMIN`
a si próprio ou a terceiros sem autorização.

7. Decisões arquiteturais consolidadas

Para o projeto `backend-api`, manteria estas decisões:

- Persistência: MySQL 8, banco `bd_paytur`, com as cinco tabelas propostas.
- ORM: Spring Data JPA e Hibernate.
- Identidade: e-mail único e senha armazenada como hash.
- Perfis: nomes sem o prefixo `ROLE_` no banco.
- Permissões: identificadores como `CONTAS_PAGAR:SELECT` e `CONTAS_PAGAR:UPDATE`.
- Conversão: `CustomUserDetailsService` transforma perfis e permissões em `GrantedAuthority`.
- Autorização: `@EnableMethodSecurity` e `@PreAuthorize`.
- Privilégios: somente as permissões explicitamente associadas aos perfis são concedidas.
- Provisionamento: criação controlada do Administrador Master, sem endpoint público para conceder privilégios administrativos.

Uma observação importante: os exemplos apresentados formam uma base de implementação, mas ainda
precisam ser integrados ao `pom.xml`, às configurações de conexão do MySQL, aos demais repositórios
e à estratégia definitiva de autenticação da API.

Também é necessário corrigir os imports e os pacotes conforme a estrutura efetiva do seu projeto.

O próximo passo técnico que recomendo é montar a primeira versão compilável do `backend-api`, 
com `pom.xml`, entidades JPA, repositórios, `SecurityConfig`, autenticação e testes básicos, antes
de implementar o CRUD de usuários e a administração dos perfis pelo RH.

Se quiser, também posso ajudar a organizar esse desenvolvimento em etapas e oferecer lembretes para retomar o projeto posteriormente.
